# Development

Deployment instructions are in the [README](../README.md) and
[deployment guide](deployment.md). See [architecture](architecture.md) for scoring
and data flow.

## Local setup

Install Node.js 24 LTS, clone the repository and run:

```sh
npm ci
cp .dev.vars.example .dev.vars
node scripts/hash-password.mjs "your-local-admin-password"
```

Use a password of at least 12 characters. Paste the printed hash into
`.dev.vars` as `ADMIN_PASSWORD_HASH`; the example signing key is for local use only.

```sh
npm run db:migrate:local
npm run build
npm run dev
```

Open `http://localhost:8787/admin` and sign in. In the RuneLite plugin, use
`http://127.0.0.1:8787` and the event join code. The explicit IPv4 address avoids
Windows machines resolving `localhost` to an IPv6 address Wrangler is not using.

After frontend changes, rebuild or run `npm run dev:web` in another terminal for
Vite hot reload through the Worker on port 8787. Stop each process with Ctrl+C.
`npm run dev:lan` exposes the Worker on the local network; use the host's LAN
address from other devices.

## Repository layout

| Path                                            | Purpose                                                   |
| ----------------------------------------------- | --------------------------------------------------------- |
| `src/screens/`, `src/components/`               | Routed pages and reusable UI                              |
| `src/apis/`, `src/routing/`                     | Named API operations and URL handling                     |
| `src/hooks/`, `src/stores/`                     | Lifecycle logic and persisted browser drafts              |
| `src/model/domain/`, `src/utils/`, `src/error/` | Models, pure helpers and error handling                   |
| `src/worker/`                                   | HTTP routes, database access, scoring and Durable Objects |
| `src/contract/`, `contract/`                    | Contract helpers and vendored plugin protocol             |
| `migrations/`                                   | Forward-only D1 schema changes                            |
| `scripts/`                                      | Deployment, generation and maintenance commands           |
| `test/`, `tools/simulator/`                     | Worker tests and a simulated plugin client                |
| `public/`                                       | Bundled fonts and artwork, with source/licence notices    |

Generated contract code, Worker binding types, build output and local runtime
state are ignored by Git. Builds use the vendored schemas and committed catalogue
data; adjacent repositories are needed only when deliberately updating the contract.

## Frontend conventions

- Use matching `Name/Name.tsx` paths and default exports for screens and components.
- Screens compose pages; reusable UI belongs in components, state/lifecycle logic
  in hooks, domain types in `model/domain`, and pure helpers in `utils`.
- Keep URLs in `routing`. Add a named `apiFetch…`, `apiCreate…` or similar operation
  under `apis`; UI modules should not call the generic admin transport directly.
- Use local state for transient interaction, TanStack Query for server data, and
  the draft store for browser persistence. Avoid duplicating the live-board cache.
- Keep local unit tests beside their modules in `__tests__`; Worker runtime tests
  belong in `test/`.
- Use two spaces, semicolons, single quotes in TypeScript/JSX, an 80-column width
  and one JSX attribute per line. Use the existing CSS/Tailwind theme and bundled
  assets. Add no dependencies on internal workplace packages.

## Checks and tests

These commands do not build or start a runtime. Unit-test HTTP calls are mocked.

```sh
npm run check:web
npm run check:worker
npm run check:unit
npm run check:structure
npm run format:web:check
npm run test:unit
npm run test:deploy
```

Web and Worker TypeScript configurations use separate DOM/Workers types. The web
client derives response types from Worker routes; keep that boundary type-only.

`npm test` is the broader suite: it generates code, builds the frontend and uses
the Workers/D1 runtime. It covers ingestion, replay, ownership, authentication and
evidence. It is separate from the local unit checks above.

## Migrations and sample data

Add new numbered migrations instead of editing applied files. Local migrations
use `npm run db:migrate:local`; deployment applies pending remote migrations before
publishing. `npm run db:migrate:remote` requires Cloudflare credentials and the
`.cache/deploy/wrangler.json` generated by setup.

To populate a running local instance:

```sh
npm run seed:local -- --code MY-GAME-01 --mode CONTROL
npm run simulate -- http://127.0.0.1:8787 MY-GAME-01
```

The seed prints a public board URL and assigns simulated players to teams.
Use a fresh game for each run; restarting simulated counters against an existing
game can produce decreasing-count flags. The simulator sends HTTP requests to
the address supplied, so use a disposable local event.

## Updating maintained data

- **Plugin contract:** run `npm run vendor:contract -- /path/to/plugin`, inspect
  the diff and `contract/VERSION`, then regenerate with `npm run generate`.
- **Drop catalogue:** `node scripts/generate-drop-catalogue.mjs` fetches OSRS Wiki
  data and updates `collectionItems.ts`. It is a manual network operation, outside
  the build.
- **Metrics:** keep names and IDs aligned with the plugin's parsers and aliases.
  A catalogue entry does not add plugin support.
- **Artwork:** keep assets local, add mappings in `src/assets/hiscore-icons.json`
  and record exact source URLs in `public/images/osrs/sources.json`.
